# Authentication

`b` supports authentication tokens for accessing private repositories and increasing API rate limits. Tokens are read from environment variables.

## Provider Tokens

| Provider | Environment Variable | Header Format |
| -------- | -------------------- | ------------- |
| GitHub   | `GITHUB_TOKEN`       | `Authorization: Bearer <token>` |
| GitLab   | `GITLAB_TOKEN`       | `PRIVATE-TOKEN: <token>` |
| Gitea / Codeberg | `GITEA_TOKEN` | `Authorization: token <token>` |

## Usage

Export the appropriate variable before running `b`:

```bash
export GITHUB_TOKEN="ghp_..."
b install owner/private-repo
```

### GitHub

A GitHub token increases the API rate limit from 60 to 5,000 requests per hour and allows access to private repositories.

`b` sends the token only over HTTPS, only on the default port, and only to `github.com` and `api.github.com`, for API requests and release downloads.
GitHub redirects a release download to a storage host. The token does not go to that host: on each redirect, `b` removes
the token unless the next URL is also HTTPS on `github.com` or `api.github.com`.

```bash
export GITHUB_TOKEN="ghp_..."
```

Without a token, `b` will show a warning when rate-limited:

> GitHub API rate limited (set GITHUB_TOKEN for higher limits)

### GitLab

A GitLab token is required for private repositories on `gitlab.com` or self-hosted instances.

```bash
export GITLAB_TOKEN="glpat-..."
```

### Gitea / Codeberg

A Gitea token is required for private repositories on Gitea or Forgejo instances like Codeberg.

```bash
export GITEA_TOKEN="..."
```

## OCI Registry Authentication

For `oci://` refs, `b` pulls images daemonlessly but reuses your local docker
credentials. It reads `~/.docker/config.json` (or the location pointed to by
`DOCKER_CONFIG`) and uses whichever helper is configured there. In other
words, if `docker login ghcr.io` works, `b install oci://ghcr.io/...` works too.

```bash
# Log in once; b picks it up automatically
docker login ghcr.io
b install oci://ghcr.io/org/private-img
```

No `b`-specific environment variable is needed for OCI auth.

## SSH Authentication

For private repos, you can also use SSH keys instead of tokens. SSH authentication uses your system's ssh-agent and works for both binaries and env sync:

```yaml
envs:
  git@github.com:org/private-infra:
    files:
      manifests/**:
        dest: manifests/
```

```bash
# Ensure your SSH key is loaded
ssh-add -l

# If not, add it
ssh-add ~/.ssh/id_ed25519

# Then install/update as normal
b update
```

SSH is often simpler than tokens for local development — no environment variables needed if your key is already in ssh-agent.

### GitHub SSH refs over HTTPS

On some machines SSH does not work, for example in a CI container without a key or in a sandbox that blocks SSH. Set `B_GIT_SSH_AS_HTTPS=1` there, and `b` fetches a GitHub SSH ref over HTTPS:

```bash
export B_GIT_SSH_AS_HTTPS=1
export GITHUB_TOKEN="ghp_..."   # for a private repo
b update
```

- Only the value `1` turns it on. When the variable is unset or has another value, SSH refs stay SSH.
- It applies to `git@github.com:org/repo` and `ssh://git@github.com/org/repo`, with or without `.git`. Such a ref then uses `https://github.com/org/repo.git`, the URL of the ref `github.com/org/repo`, with the same token rules as that ref.
- These commands send `GITHUB_TOKEN` to `github.com` in a header for such a ref: `b update` and `b install` when they sync an env, and `b install`, `b update` and `b version` for a binary from a git ref (`git@github.com:org/repo:path/to/file`).
- These commands send no token, so git uses your credential helper, if you have one: `b env status`, `b env add`, `b env match`, `b env profiles`, the env list of `b version`, the `b.yaml` hint of `b install` for a repo with no release, and the `[d]iff` choice of `b update`.
- Refs for other hosts stay SSH: GitLab, Gitea, a self-hosted server, and also a GitHub ref with another user, a port or another host name (`ssh.github.com`).
- Your `b.yaml` and `b.lock` do not change: the key stays the SSH ref. The cache directory stays the same too. A cache that an SSH clone made is fetched over HTTPS while the variable is on.
- There is no fallback. Without the variable, an SSH ref that fails is an error, as before.
- Your own git URL rewrites still apply, also in the other direction. With `url.git@github.com:.insteadOf https://github.com/` in your git config, git fetches such a ref over SSH again, and the variable has no effect.

Before this variable, the workaround was git's own URL rewrite. It still works, and it is the option for another host:

```bash
GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0='url.https://github.com/.insteadOf' GIT_CONFIG_VALUE_0='git@github.com:' \
GIT_CONFIG_KEY_1='credential.helper' GIT_CONFIG_VALUE_1='!gh auth git-credential' \
b update
```

`b` sends no header for an SSH ref, so it keeps these variables. For an HTTPS ref with a token, `b` sets its own `GIT_CONFIG_COUNT`, and git then does not read these entries for that ref.

### The token in git commands

For a git clone, fetch or ls-remote over HTTPS, `b` gives the token to git as the header key `http.https://<host>/.extraHeader`. The key is in `GIT_CONFIG_*` environment variables, not on the command line.

- `b` reads the host and the port from the HTTPS URL of the ref one time. That host selects the token. That host and port go into the key. For a port that is not the default, the key is `http.https://<host>:<port>/.extraHeader`.
- A ref with the scheme `https://` (in upper case or lower case) is the same as the ref without the scheme. For example, `https://github.com/org/repo` gets the URL `https://github.com/org/repo.git` and the same token as `github.com/org/repo`, for the same host. A ref that ends in `.git` gets the same URL and token as the ref without `.git`. A ref with another scheme, for example `http://` or `file://`, is refused (see below). `ssh://` and `git://` refs do not change. These two schemes are lower case only: `SSH://` and `GIT://` are refused.
- The token of a provider goes to its host and to the subdomains of that host, on all ports. For example, `GITHUB_TOKEN` goes to `github.com` and to `api.github.com`. Upper case and lower case are the same. A host with a trailing dot (`github.com.`) gets no token.
- `b` refuses some refs. A refused ref gets no token, and `b` runs no remote git command (clone, fetch or ls-remote) for it. `b` refuses a ref with one of these in the host part:
  - a user name or a password (`user@`, `user:password@`)
  - no host
  - a port that is not a number from 1 to 65535
  - a host character that is not a letter, a digit, a hyphen or a dot, for example `*`, `%` or `_`. `b` accepts an IPv6 address in brackets.
- The key protects the token against a rewrite of the initial URL. git compares the key with the URL after your own `url.<base>.insteadOf` rewrites. Thus a rewrite to another host does not get the token.
- The key does not protect the token after a redirect. git does not compare the key with the URL of a redirect. What git and libcurl do with the header after a redirect to another host is their behavior. It is not a check that `b` does.

`b` also sets `GIT_TERMINAL_PROMPT=0` for these git commands. Thus git does not ask for a user name or a password on the terminal. A private repo with no token and no credential helper fails at once.

What an error message shows:

- The token never shows. In the error message of these git commands, `b` shows `***` in place of the token.
- In a ref or a URL that `b` writes in an error message, `b` shows `***` in place of the user part (`user:password@`). The host part ends at the first `/`, `?` or `#`. The env lines of `b version` name each env by its key in `b.yaml`, as you wrote it. `b update` does the same, but for a key that the ref check below refuses, its `✗` line and its failure summary show `<refused env key>`.
- `b` refuses these refs first, before a message shows the ref, with a fixed text that does not show the ref. The ref gets no token, and no git command runs. `b env add`, `b env match`, `b env profiles`, the sync of an env and a binary from a git ref do this check:
  - a ref without a scheme with a password in front of its host (`user:password@host`), a ref with more than one `@` in front of its host (`user:p@ss@host/org/repo`, `git@x@github.com:org/repo`, `ssh://git@x@github.com/org/repo`), and a ref with an `@` after a second `://` (`https://a?b://user:password@host/x`):
    `refusing a git ref with a password or more than one @ before its path: remove the user part`
  - An `https://` ref with one `@` (`https://user:password@host/org/repo`) gets the host error, with `***` in place of the user part.
- `b` checks the transport of each URL before a clone, fetch or ls-remote. This includes the URL that a clone stored in its cache. These forms pass: `https://` (in upper case or lower case, with the host check above), `ssh://` (lower case only), an scp-like URL (`git@host:org/repo`) and a local path. `b` refuses the other forms with a fixed text, and git does not run:
  - another scheme (`http://`, `file://`, `ftp://`, `SSH://`, a `git://` URL), a second `://`, or a git remote helper (`<transport>::<address>`):
    `refusing a git ref with a scheme that b does not fetch: use https://, ssh://, git:// or no scheme`
  - more than one `@` in the host part of an `https://`, `ssh://` or scp-like URL: the first fixed text above.
  - A `git://` ref is the `b` form for a repo and a file in it. `b` changes it to a local path or an `https://` URL before git runs, so a `git://` URL does not get to git.

Do not put a password in a ref. `b` finds the user part only in front of the host. A raw `/`, `?` or `#` in a password ends the host part early, so `b` does not see a user part, and the message can show a part of the password. An `ssh://` ref with a password (`ssh://user:password@host/org/repo`) goes to git as it is: git or ssh can show the password in their own error output. Your `b.yaml` and `b.lock` keep the ref as you wrote it.

## CI/CD

In CI/CD pipelines, use secrets or environment variables provided by your CI system:

```yaml
# GitHub Actions
steps:
  - name: Install tools
    env:
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    run: b install

# GitLab CI
install_tools:
  script:
    - b install
  variables:
    GITLAB_TOKEN: $GITLAB_API_TOKEN
```
