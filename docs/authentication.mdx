# Authentication

`b` supports authentication tokens for accessing private repositories and increasing API rate limits. Tokens are read from environment variables.

## Provider Tokens

| Provider | Environment Variable | Header Format |
| -------- | -------------------- | ------------- |
| GitHub   | `GITHUB_TOKEN`       | `Authorization: Bearer <token>` |
| GitLab   | `GITLAB_TOKEN`       | `PRIVATE-TOKEN: <token>` |
| Gitea / Codeberg | `GITEA_TOKEN` | `Authorization: token <token>` |

## Usage

Export the appropriate variable before running `b`:

```bash
export GITHUB_TOKEN="ghp_..."
b install owner/private-repo
```

### GitHub

A GitHub token increases the API rate limit from 60 to 5,000 requests per hour and allows access to private repositories.

`b` sends the token only over HTTPS, only on the default port, and only to `github.com` and `api.github.com`, for API requests and release downloads.
GitHub redirects a release download to a storage host. The token does not go to that host: on each redirect, `b` removes
the token unless the next URL is also HTTPS on `github.com` or `api.github.com`.

```bash
export GITHUB_TOKEN="ghp_..."
```

Without a token, `b` will show a warning when rate-limited:

> GitHub API rate limited (set GITHUB_TOKEN for higher limits)

### GitLab

A GitLab token is required for private repositories on `gitlab.com` or self-hosted instances.

```bash
export GITLAB_TOKEN="glpat-..."
```

### Gitea / Codeberg

A Gitea token is required for private repositories on Gitea or Forgejo instances like Codeberg.

```bash
export GITEA_TOKEN="..."
```

## OCI Registry Authentication

For `oci://` refs, `b` pulls images daemonlessly but reuses your local docker
credentials. It reads `~/.docker/config.json` (or the location pointed to by
`DOCKER_CONFIG`) and uses whichever helper is configured there. In other
words, if `docker login ghcr.io` works, `b install oci://ghcr.io/...` works too.

```bash
# Log in once; b picks it up automatically
docker login ghcr.io
b install oci://ghcr.io/org/private-img
```

No `b`-specific environment variable is needed for OCI auth.

## SSH Authentication

For private repos, you can also use SSH keys instead of tokens. SSH authentication uses your system's ssh-agent and works for both binaries and env sync:

```yaml
envs:
  git@github.com:org/private-infra:
    files:
      manifests/**:
        dest: manifests/
```

```bash
# Ensure your SSH key is loaded
ssh-add -l

# If not, add it
ssh-add ~/.ssh/id_ed25519

# Then install/update as normal
b update
```

SSH is often simpler than tokens for local development — no environment variables needed if your key is already in ssh-agent.

### GitHub SSH refs over HTTPS

On some machines SSH does not work, for example in a CI container without a key or in a sandbox that blocks SSH. Set `B_GIT_SSH_AS_HTTPS=1` there, and `b` fetches a GitHub SSH ref over HTTPS:

```bash
export B_GIT_SSH_AS_HTTPS=1
export GITHUB_TOKEN="ghp_..."   # for a private repo
b update
```

- Only the value `1` turns it on. When the variable is unset or has another value, SSH refs stay SSH.
- It applies to `git@github.com:org/repo` and `ssh://git@github.com/org/repo`, with or without `.git`. Such a ref then uses `https://github.com/org/repo.git`, the URL of the ref `github.com/org/repo`, with the same token rules as that ref.
- These commands send `GITHUB_TOKEN` to `github.com` in a header for such a ref: `b update` and `b install` when they sync an env, and `b install`, `b update` and `b version` for a binary from a git ref (`git@github.com:org/repo:path/to/file`).
- These commands send no token, so git uses your credential helper, if you have one: `b env status`, `b env add`, `b env match`, `b env profiles`, the env list of `b version`, the `b.yaml` hint of `b install` for a repo with no release, and the `[d]iff` choice of `b update`.
- Refs for other hosts stay SSH: GitLab, Gitea, a self-hosted server, and also a GitHub ref with another user, a port or another host name (`ssh.github.com`).
- Your `b.yaml` and `b.lock` do not change: the key stays the SSH ref. The cache directory stays the same too. A cache that an SSH clone made is fetched over HTTPS while the variable is on.
- There is no fallback. Without the variable, an SSH ref that fails is an error, as before.
- Your own git URL rewrites still apply, also in the other direction. With `url.git@github.com:.insteadOf https://github.com/` in your git config, git fetches such a ref over SSH again, and the variable has no effect.

Before this variable, the workaround was git's own URL rewrite. It still works, and it is the option for another host:

```bash
GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0='url.https://github.com/.insteadOf' GIT_CONFIG_VALUE_0='git@github.com:' \
GIT_CONFIG_KEY_1='credential.helper' GIT_CONFIG_VALUE_1='!gh auth git-credential' \
b update
```

`b` sends no header for an SSH ref, so it keeps these variables. For an HTTPS ref with a token, `b` sets its own `GIT_CONFIG_COUNT`, and git then does not read these entries for that ref.

### The token in git commands

For a git clone, fetch or ls-remote over HTTPS, `b` gives the token to git as the header key `http.https://<host>/.extraHeader`. The key is in `GIT_CONFIG_*` environment variables, not on the command line. It has the host of the ref, so git sends the header to that host only. git compares the key with the URL after your own `url.<base>.insteadOf` rewrites: a rewrite to another host does not get the token.

`b` also sets `GIT_TERMINAL_PROMPT=0` for these git commands. Thus git does not ask for a user name or a password on the terminal. A private repo with no token and no credential helper fails at once.

## CI/CD

In CI/CD pipelines, use secrets or environment variables provided by your CI system:

```yaml
# GitHub Actions
steps:
  - name: Install tools
    env:
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    run: b install

# GitLab CI
install_tools:
  script:
    - b install
  variables:
    GITLAB_TOKEN: $GITLAB_API_TOKEN
```
